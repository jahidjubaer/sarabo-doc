Customer "Create request" চাপলে কী কী হয়? File ধরে বলো।

RepairRequestV2Form.jsx form validate করে api/repairRequests.js-এর createRepairRequestV2() ডাকে → POST /repair-requests। useAxiosSecure token লাগায়। Server-এ routes/repairRequests.js: verifyFBToken, verifyEmailVerified → repairRequestController.createRepairRequest() → v2 হলে createRepairRequestV2()। সেখানে hasTechnicianFor() (region gate), checkSlot() (slot capacity), price snapshot, generateSecureTrackingId(), insert, তারপর notification/email/job announcement। Response-এ request id আর tracking code; client "Request created" দেখায় (photo add করার option)।

Technician offer পাঠানোর API call কোথা থেকে যায়?

components/technician/JobApplicationSheet.jsx → api/jobPortal.js → POST /repair-requests/:id/applications → routes/jobPortal.js (verifyFBToken, verifyTechnician) → jobPortalController.apply()। Validation utils/jobPortal.js-এ (estimate range, fee minimum থেকে catalogue fee)।

Payment "paid" কোথায় হয়? Success page-এ?

না। Success page শুধু দেখায়। আসল "paid" হয় POST /stripe-webhook-এ: routes/paymentWebhook.js raw body নেয়, paymentController.handleStripeWebhook() stripe.webhooks.constructEvent() দিয়ে signature verify করে, তারপর services/paymentProcessor.js transaction-এ payment row, request status আর settlement লেখে। একই event দুইবার এলে দ্বিতীয়বার কিছু হয় না (idempotent)।

Commission হিসাবের code দেখাও।

utils/settlement.js। Base = partsAmount + laborAmount + additionalCharges (= quote total)। Commission = integer ratio 10/100, আর technician-এর অংশ = subtotal − commission (বিয়োগ করে, আলাদা % নয়), তাই সবসময় commission + receivable = subtotal। Parts/labour কীভাবে ভাগ করল তাতে কারো টাকা বদলায় না।

Double booking কীভাবে আটকানো হয়েছে, code-এ কোথায়?

services/jobBooking.js → bookApplication()। Transaction-এর ভেতরে technician-এর অন্য active request আছে কি না দেখে (ACTIVE_STATUSES), request update-এর filter-এ deliveryStatus: 'pending-pickup' আর technicianId নেই এমন শর্ত, technician update-এ workStatus: 'available' শর্ত। দুইজন একসাথে চাপলে একজনের update match করে না → সব rollback।

Role check কোথায়? Client-এ লুকিয়ে রাখলেই কি যথেষ্ট?

না। Client guard (routes/AdminRoute.jsx ইত্যাদি) শুধু UI। Server-এ middleware/auth.js: verifyAdmin (role !== 'admin' → 403), verifyTechnician (role !== 'rider' → 403)। তার উপর controller দেখে এই request-এর owner/assigned technician কি না, আর বর্তমান state-এ এই কাজ চলে কি না।

Pickup slot-এর নিয়ম কোথায়?

utils/pickupSlots.js: PICKUP_SLOTS (৪টা), CLOSED_WEEKDAYS = [5] (শুক্রবার), BOOKING_WINDOW_DAYS = 7, MIN_LEAD_MINUTES = 60, DEFAULT_SLOT_CAPACITY = 3, সময় Asia/Dhaka। Availability দেখায় GET /pickup-slots (pickupSlotController), reschedule PATCH /repair-requests/:id/pickup-slot।

AI summary যে ভুল সংখ্যা বলে না, তার code?

services/aiReportSummaryService.js: buildSummaryFacts() শুধু aggregate বানায়; allowedNumbers() সেই facts-এর সব সংখ্যার set; onlyKnownNumbers() প্রতিটা sentence-এর সংখ্যা চেক করে, অজানা হলে বাদ (ছোট সংখ্যা ≤10 আর 24/30/90 context হিসেবে চলে)।

Status কোথায় define করা? "parcel", "rider" কেন?

utils/repairRequestStatus.js। প্রজেক্ট একটা parcel-delivery codebase থেকে শুরু হয়েছিল; data নষ্ট না করার জন্য stored value (rider, parcel_picked_up, deliveryStatus) রেখে দিয়েছি — এটা internal contract। User সবসময় repair শব্দ দেখে (Technician, Device collected)। পরিকল্পিত migration future work-এ আছে।

৫. সম্ভাব্য প্রশ্ন — General / Design

এটা কি শুধু একটা CRUD app না?

না। Repair একটা case যেটার 14টা state; প্রতিটা action-এ server role + current state চেক করে। টাকা আর assignment বদলানোর সব কাজ MongoDB transaction-এ, deadline আছে যাতে কিছু আটকে না থাকে, আর payment webhook-ভিত্তিক।

MongoDB কেন, SQL কেন না?

একটা repair request নিজের quote, inspection, history, settlement নিয়ে একটা document — document database-এ মানায়। আলাদা collection-এর মধ্যে consistency রাখতে MongoDB multi-document transaction (replica set) ব্যবহার করেছি। Relational হলেও করা যেত; এটা trade-off, ভুল-সঠিক না।

Firebase Auth কেন? নিজে JWT বানালে না কেন?

Password রাখা, email verification, Google login, token refresh — নিরাপদভাবে নিজে বানানো ঝুঁকিপূর্ণ। Firebase ID token server-এ Firebase Admin দিয়ে verify করি; role নিজের DB-তে।

Serverless (Vercel) কেন? সমস্যা কী?

Free, push করলেই deploy, scale নিজে থেকে। সমস্যা cold start — প্রথম request ধীর। API Mumbai region-এ সরিয়ে (DB-র পাশে) cold 10.7s → 2.9s, warm 0.75s → 0.2s হয়েছে। Rate limit memory-তে রাখা যায় না বলে MongoDB store।

Frontend-এ state কীভাবে manage করেছ?

Server data TanStack Query দিয়ে (cache, refetch, mutation-এর পর invalidate; key গুলো hooks/*Keys.js-এ)। Form-এ react-hook-form। Global client state কম — login Firebase context-এ।

ER diagram বুঝিয়ে বলো।

User অনেক repair request করে, technician-ও হতে পারে (technicians collection)। প্রতিটা request একটা service definition দিয়ে priced, অনেক job application (offer) পায়, তার payment rows, একটা review, সর্বোচ্চ ২টা warranty claim। Quote আর inspection request-এর ভেতরেই embedded। Withdrawal technician-এর সাথে।

তুমি নিজে কী করেছ?

পুরো project আমার: requirement, design, server আর client code, test, deploy, report। AI tool সাহায্য হিসেবে ব্যবহার করেছি, কিন্তু প্রতিটা feature-এর rule আর code আমি বুঝি — যেকোনো file খুলে বোঝাতে পারব।

পুরো Bangla interface নেই কেন?

AI helper বাংলা/Banglish ইনপুট বোঝে, offer note বাংলায় লিখতে পারে; কিন্তু পুরো UI localisation করিনি — future work।

একজন technician একসাথে একটাই job কেন?

Cash দিলে platform-এর ১০% আর হিসাব রাখা কঠিন। Future work: hand-over-এ cash, তারপর wallet থেকে platform share কাটা।

Load test বা security audit হয়েছে?

Signed-in page-এর browser test নেই কেন?

৭. Edge case প্রশ্ন

Technician fee নিয়ে এলোই না (no-show)?

Admin "missed pickup" থেকে withdraw করে (POST /admin/repair-requests/:id/missed-pickup/withdraw, missedPickupController) → fee পুরো refund, ওই offer no_show, job আবার open। No-show reliability score কমায়।

Customer বাসায় ছিল না?

Technician নোটসহ "Customer wasn't available" চাপে (POST …/customer-not-available, workflowController.customerNotAvailable())। Request-এ pickupRescheduleRequestedAt বসে, customer-কে নতুন pickup সময় বেছে নিতে বলা হয়। Technician-ই না এলে সেটা আলাদা — admin-এর missed-pickup flow (ask-new-time বা withdraw)।

একই সময়ে দুইজন customer slot-এর শেষ জায়গা নিলে?

Capacity check হয়, কিন্তু lock নেই — একই সেকেন্ডে দুইজন পেতে পারে। এটা limitation-এ লেখা; এখনকার scale-এ ঠিক আছে, busy হলে atomic counter লাগবে।

Payment দিয়ে দিল, কিন্তু ঠিক তখন অন্য offer বেছে নেওয়া হয়েছে / request cancel?

Webhook-এ bookApplication() JOB_NOT_OPEN বা TECHNICIAN_BUSY ফেরত দেয় → কিছু book হয় না → fee নিজে থেকে refund। Cancel-এর পরে দেরিতে আসা payment-ও refund হয়।

Stripe refund fail করলে?

Refund "pending" থাকে, admin attention list-এ "Refund waiting" দেখায়, admin retry করে (POST /admin/repair-requests/:id/inspection-fee/retry-refund)। Idempotency key থাকায় retry-তে double refund হয় না।

Customer quote approve করল কিন্তু টাকা দিল না?

৩ দিন পর cron বন্ধ করে দেয় (closeUnpaidApprovedQuotes)। Customer নিজেও cancel-unpaid করতে পারে।

Customer quote decline করল, তারপর কিছুই করল না?

Technician revise করে নতুন quote দিতে পারে; নয়তো ৩ দিন পর auto close (declinedQuoteClose.js), fee রাখা হয় (technician ৯০%)।

Phone repair করা যাবে না?

Inspection-এ "Not repairable / Not economical" → POST …/close-not-repairable; fee রাখা হয় কারণ technician পরিদর্শন করেছে।

Repair শুরু করে technician শেষ করতে পারল না?

"Can't finish this repair" (POST …/repair/cannot-complete) → admin-এর কাছে যায় → admin cancel-paid-repair দিয়ে refund করে, device ফেরতের confirm আলাদা step।

Customer বলছে phone ফেরত পায়নি?

"I haven't received it" → receipt-dispute, admin সিদ্ধান্ত দেয়। ততক্ষণ technician-এর টাকা pending থাকে।

Customer confirm-ই করে না?

Technician "returned" mark করার ৩ দিন পর auto confirm (receiptConfirmation.js, method 'auto')।

Warranty-র অপব্যবহার — নতুন করে ফেলে দিয়ে claim করলে?

Covered শুধু একই fault ফিরে এলে বা লাগানো part নষ্ট হলে। Technician free re-inspection-এ দেখে "Not covered" (new damage, water, drop) দিতে পারে কারণসহ; customer admin review চাইতে পারে। Pickup condition record এখানে প্রমাণ।

Technician warranty claim ignore করলে?

প্রতিটা step-এর deadline (book 3 দিন, decide 3 দিন, re-repair 7 দিন)। মিস হলে overdue → admin take over → দরকারে refund।

Warranty refund-এর আগে technician টাকা তুলে নিলে?

Settlement reversed হয়; আগে তোলা টাকা "owed" হিসেবে দেখায় আর পরের আয় থেকে কাটা হয় (calculateWallet)।

Admin technician remove করল, কিন্তু তার wallet-এ টাকা আছে?

Remove-এর সময় একই transaction-এ পুরো available balance bKash withdrawal হিসেবে queue হয় (services/technicianRemovalPayout.js); আগে preview দেখায় (GET /technicians/:id/final-payout)। Open warranty claim থাকলে remove করা যায় না।

Request চলাকালীন admin দাম বদলালে?

পুরনো request-এ price snapshot থাকে; নতুন দাম শুধু নতুন request-এ (pricingRule.version)।

Region-এ কোনো technician নেই?

Request নেওয়াই হয় না (409, কারণসহ), customer অপেক্ষায় পড়ে থাকে না; turned-away count admin report-এ দেখায় — কোথায় technician লাগবে।

AI বন্ধ / ধীর / quota শেষ?

সব AI optional। Timeout আছে (aiHelperCall.js), support chat-এ fallback model; বন্ধ হলে form হাতে পূরণ করা যায়, বাকি app স্বাভাবিক।

Webhook দেরিতে এলো, customer page reload করল?

Page শুধু দেখায়; webhook এলে state বদলায়। দুইবার এলেও একবার record।

Customer দুইবার checkout খুললে?

services/checkoutSessionManager.js একটা request-এ একটাই খোলা checkout রাখে (claim + TTL), Stripe create-এ idempotency key।

৮. Security প্রশ্ন

কেউ অন্যের request id দিয়ে data দেখতে পারবে?

না। Controller দেখে caller owner, assigned technician বা admin কি না; নাহলে 403/404। Public tracking-এ কোনো personal data নেই।

Tracking code অনুমান করা যাবে?

128-bit random (crypto.randomBytes(16)) — কার্যত অসম্ভব। আর দেখালেও শুধু stage দেখায়।

Photo-র link share করলে?

Bucket private; link কয়েক মিনিটের signed URL, তারপর অকেজো। Upload-এর পর আসল type ও size আবার verify করা হয়।

NoSQL injection?

Input-এর type/shape validate করা হয় (utils/* validator), search text escape (utils/searchSanitize.js), ObjectId parse-এর আগে চেক।

Secret কোথায়?

শুধু server environment variable-এ (Vercel); repo বা browser-এ না। .env.example-এ শুধু নাম। Log-এ request body লেখা হয় না (utils/safeLogger.js)।

CORS আর rate limit?

config/cors.js-এ allow-list (production-এ শুধু Vercel client)। AI chat-এ per-IP/per-user আর site-wide limit, MongoDB-তে রাখা।

Cron URL কেউ নিজে call করলে?

Secret (CRON_SECRET) না মিললে কিছু চলে না; secret ছাড়া configure না থাকলে 503।

Email verify না করে কেউ request বা payment করতে পারবে?

না — verifyEmailVerified middleware 403 দেয় (create request, payment, review, warranty claim-এ)।

৯. AI প্রশ্ন

AI কি দাম বানিয়ে বলতে পারে?

না। কোনো AI feature দাম সেট করে না। Support chat-এর দাম live catalogue থেকে prompt-এ যায়; request helper শুধু catalogue id বেছে নেয়, server আবার চেক করে।

Customer-এর personal data AI-তে যায়?

নাম, email, card কিছু পাঠানো হয় না। Request helper-এ শুধু customer-এর লেখা আর (দিলে) photo — form-এ সতর্কবার্তা আছে। Report summary শুধু aggregate সংখ্যা।

AI ভুল উত্তর দিলে?

Output schema validate হয়; ভুল হলে বাদ। Helper-এর সব suggestion customer বদলাতে পারে, Undo আছে। AI ছাড়াই সব কাজ করা যায়।

AI কত দ্রুত? আগে fail করত কেন?

আগের model ধীর ছিল, timeout হতো। এখন gemini-3.5-flash-lite, fail করলে fallback model; live-এ 1.4–1.9s।

১০. Testing আর deployment

কীভাবে test করেছ?

2,761 server test, real HTTP দিয়ে, real MongoDB replica set-এ (transaction চালাতে), Stripe/AI/storage fake। Race test-ও আছে (দুই admin একসাথে assign)। Client-এ 58 Playwright browser test (desktop + mobile)। GitHub Actions প্রতিটা push-এ; সব pass হলে তবেই main-এ push।

Test DB আর production DB আলাদা?

হ্যাঁ। Test throwaway/in-memory MongoDB-তে চলে, কখনো আসল credential দিয়ে না। Production server secret আর https origin ছাড়া start-ই হয় না।

Migration কীভাবে করেছ (যেমন minimum fee)?

Script আগে dry-run (কী বদলাবে দেখায়), তারপর confirm flag দিয়ে চালানো; production guard আছে। Minimum fee migration production আর local দুটোতেই চালানো হয়েছে।

১১. কঠিন / ব্যক্তিগত প্রশ্ন

সবচেয়ে কঠিন অংশ কী ছিল?

টাকা আর state একসাথে ঠিক রাখা — payment, booking, refund, settlement যেন কখনো অর্ধেক না হয়। এর জন্য transaction, webhook-as-truth আর idempotency key। আর "কোনো request আটকে থাকবে না" — প্রতিটা waiting state-এ deadline বা admin alert।

আবার শুরু করলে কী বদলাতে?

শুরু থেকেই repair domain-এর নাম (parcel/rider legacy না রেখে), local payment gateway, আর slot capacity-র জন্য atomic counter।

এটা কি আসলে চালু করা যাবে?

Technically deploy করা আছে, live। বাস্তবে চালুর আগে লাগবে: local payment gateway, আসল দাম (repair shop-এর সাথে ঠিক করা), technician verification প্রক্রিয়া, আর load/security test।

Business model কী?

প্রতিটা repair-এ ১০% commission (kept inspection fee-তেও একই ভাগ)। Customer বাড়তি কিছু দেয় না।

অন্য platform থেকে আলাদা কীভাবে?

Inspection-এর পর itemised quote, approve-এর আগে চার্জ নেই, condition record, 30-দিনের warranty workflow, region-ভিত্তিক matching আর ranking, আর technician-এর guaranteed payment (আগে online payment, receipt confirm-এ release)।

১২. Theory / concept প্রশ্ন (basic জিনিস, কিন্তু প্রায়ই জিজ্ঞেস করে)

REST API কী? তোমার API কি RESTful?

Resource-ভিত্তিক URL আর HTTP method দিয়ে কাজ: GET /repair-requests/:id পড়া, POST /repair-requests তৈরি, PATCH আংশিক বদল, DELETE মোছা। Stateless — প্রতিটা request-এ token যায়, server session রাখে না। যেখানে কাজটা "action" (যেমন accept, cancel-booking), সেখানে sub-resource action path দিয়েছি: POST …/applications/:id/accept।

Middleware কী? তোমার project-এ উদাহরণ দাও।

Request controller-এ পৌঁছানোর আগে মাঝখানে চলা function, যেটা next() ডাকে বা response দিয়ে থামিয়ে দেয়। উদাহরণ: verifyFBToken (token না থাকলে 401), verifyAdmin (403), ensureDatabaseReady, requestId (প্রতিটা request-এ id), supportRateLimit। সব middleware/ folder-এ।

Firebase ID token আর JWT-র সম্পর্ক কী?

Firebase ID token একটা signed JWT (মেয়াদ ১ ঘণ্টা)। Client getIdToken() দিয়ে নেয়, header-এ পাঠায়; server admin.auth().verifyIdToken() দিয়ে signature আর মেয়াদ চেক করে email, email_verified বের করে। মেয়াদ শেষ হলে interceptor নতুন token নিয়ে একবার retry করে।

CORS কী, কেন লাগে?

Browser অন্য domain-এর API call আটকায়, যদি না server বলে "এই origin চলবে"। আমার client আর API আলাদা domain-এ, তাই config/cors.js-এ allow-list: production-এ শুধু Vercel client, dev-এ localhost:5173। অন্য site থেকে কেউ API চালাতে পারবে না browser দিয়ে।

Transaction আর ACID বুঝিয়ে বলো, তোমার কোথায় লেগেছে?

কয়েকটা write হয় সব একসাথে হবে, নয়তো একটাও না (Atomicity); data সবসময় নিয়মে থাকে (Consistency); একসাথে চলা কাজ একে অন্যকে নষ্ট করে না (Isolation); commit হলে থেকে যায় (Durability)। Booking-এ request, technician আর সব offer একসাথে বদলায়; payment-এ payment row + status + settlement। session.withTransaction() — যেমন services/jobBooking.js, services/paymentProcessor.js, services/requestClosure.js। Multi-document transaction-এর জন্য MongoDB replica set লাগে।

Idempotency কী? কোথায় ব্যবহার করেছ?

একই কাজ একাধিকবার হলেও ফল একবারের মতো। Stripe-এ checkout create আর refund-এ idempotencyKey (যেমন inspection-refund-<sessionId>); webhook একই event দুবার এলে একবার record (payments.sessionId unique index); notification-এ deduplicationKey unique; email-এ email_log; receipt confirm confirmReceiptOnce()।

Webhook কী? Redirect URL দিয়ে কেন payment confirm করোনি?

Webhook = Stripe নিজে থেকে আমার server-কে POST করে জানায় "payment হয়েছে"। Redirect URL-এ user নিজে যায় — বন্ধ করে দিতে পারে, বা বানিয়ে URL খুলতে পারে। তাই redirect শুধু দেখায়, সত্য হলো signature-verified webhook।

SPA কী? SEO-র সমস্যা?

React single-page app: একবার load, তারপর route বদলায় browser-এ। Dashboard-এর জন্য ঠিক আছে। Public page-এর SEO দুর্বল হতে পারে — দরকার হলে SSR/pre-render (যেমন Next.js) future-এ। Project-এর মূল কাজ logged-in workflow, তাই SPA বেছেছি।

HTTP status code কোনগুলো ব্যবহার করেছ, কেন?

400 ভুল input, 401 login নেই/token ভুল, 403 login আছে কিন্তু অনুমতি নেই (role, email not verified), 404 নেই বা দেখার অধিকার নেই, 409 state conflict (যেমন NO_TECHNICIAN_AVAILABLE, PICKUP_SLOT_FULL, BKASH_TRX_ID_ALREADY_USED), 429 rate limit, 503 service configure হয়নি (যেমন AI বা cron)। প্রতিটা error-এর সাথে একটা স্থির code থাকে, client সেটা দেখে message দেখায়।

Signed URL কী?

Storage-এর একটা link যেটায় সই আর মেয়াদ লাগানো — যার কাছে আছে সে নির্দিষ্ট সময় পর্যন্ত শুধু ওই একটা file পড়তে/লিখতে পারে। Upload-এর জন্য upload URL, দেখার জন্য কয়েক মিনিটের read URL; bucket নিজে private।

Cron job কী? Serverless-এ কীভাবে চালালে?

নির্দিষ্ট সময়ে নিজে থেকে চলা কাজ। Serverless-এ সবসময় চলা process নেই, তাই Vercel Cron প্রতিদিন একটা URL call করে (vercel.json), আর server secret চেক করে কাজ চালায়।

Cold start কী?

অনেকক্ষণ request না এলে serverless function ঘুমিয়ে পড়ে; পরের request-এ নতুন করে চালু হতে সময় লাগে (DB connect, index চেক)। Region DB-র পাশে এনে কমিয়েছি; free uptime ping দিলে আরও কমত।

১৩. Database আর index প্রশ্ন

কোন কোন collection আছে?

মূল: users, technicians, repair_requests, service_definitions, jobApplications (offer), payments, withdrawals, warranty claims, notifications, trackingEvents, reviews/reports। সহায়ক: checkoutSessions, upload session, email_log, turned_away_requests, ai_report_summaries, rate-limit store। পুরো তালিকা report-এর Chapter 4 table-এ।

Index কী? কয়টা আর কেন?

Index = দ্রুত খোঁজার জন্য সাজানো তালিকা, আর unique index নিয়মও চাপায়। Server start-এ 44টা createIndex (config/database.js)। উদাহরণ: trackingId unique; payments.sessionId unique (একই Stripe session দুবার না); review প্রতি repair-এ একটা (reviews_repair_unique); প্রতি technician প্রতি request-এ একটাই offer (jobApplications_request_technician_unique)।

Partial unique index কোথায়, কেন?

শুধু কিছু document-এর উপর unique: (১) technician-এর একসাথে একটাই খোলা withdrawal — partialFilterExpression: { status: 'requested' }; (২) bKash TrxID একবারই — শুধু যেখানে payoutReference string; (৩) একটা request-এ একটাই active checkout — { active: true }। App code ভুল করলেও database নিজেই আটকায়।

TTL index কী?

সময় হলে MongoDB নিজে document মুছে দেয় (expireAfterSeconds)। ব্যবহার: email_log (90 দিন), turned_away_requests (180 দিন), rate-limit counter, পুরনো warranty photo upload session।

Embedded রাখলে কেন, আলাদা collection কেন না (quote, inspection)?

Quote আর inspection সবসময় একটা request-এর সাথে পড়া হয় আর একটা request-এর একটাই চলতি quote — embed করলে এক read-এ পুরো case। Offer আলাদা collection, কারণ একটা request-এ অনেক offer, আর technician-এর দিক থেকেও খোঁজা লাগে।

Balance কেন store করোনি?

Store করলে কোনো bug-এ সংখ্যা আর record আলাদা হয়ে যেতে পারে। প্রতিবার settlement আর withdrawal থেকে হিসাব (calculateWallet), তাই "drift" হতে পারে না। Data কম, তাই খরচও কম।

Price snapshot মানে কী?

Request তৈরির সময় service-এর দাম আর version request-এ কপি রাখা। পরে admin দাম বদলালেও পুরনো request-এর দাম বদলায় না।

১৪. Frontend প্রশ্ন

Page গুলো কীভাবে load হয়? Bundle বড় না?

Route-ভিত্তিক lazy loading: routes/router.jsx-এ lazy(() => import(...)), আর RouteSuspense loading দেখায়। দরকারি page-এর code তখনই আসে।

Data fetch-এ useEffect + useState না করে TanStack Query কেন?

Cache, loading/error state, retry, background refetch আর mutation-এর পর invalidate নিজে থেকে। যেমন job board প্রতি 60 সেকেন্ডে refresh (refetchInterval, hooks/useJobPortal.js)। Query key গুলো এক জায়গায় (hooks/*Keys.js), তাই ভুল cache কম।

Form validation কোথায়? Client-এ করলেই হয়?

Client-এ react-hook-form দিয়ে তাড়াতাড়ি ভুল দেখানো (UX), কিন্তু আসল validation server-এ (utils/repairRequestV2.js, utils/quote.js, utils/jobPortal.js …), কারণ client bypass করা যায়।

এক page তিন role-এর জন্য কীভাবে আলাদা দেখায়?

RequestDetails.jsx viewer role বের করে (utils/workspacePresentation.js) আর Customer/Technician/Admin view render করে। সবার উপরে একই ৪-ধাপের spine; "Your next step" panel শুধু ওই role-এর কাজ দেখায়।

UX-এর জন্য আর কী করেছ?

Dark/light mode (ThemeToggle.jsx), Ctrl+K command menu (CommandMenu.jsx), নতুন user-এর জন্য product tour (react-joyride, components/tour/SaraboTour.jsx), mobile layout (MobileTabBar.jsx, MobileActionBar.jsx), empty/loading/error state component, chart-এর পাশে "Show as a table"।

Map কীভাবে করেছ? Google Maps না কেন?

Leaflet + OpenStreetMap (free)। Area data public/serviceAreas.json; sub-area-র coordinate একবার offline-এ বের করে রাখা, browser-এ geocoding হয় না। Google Maps-এ API key আর billing লাগে।

১৫. Notification আর email

Notification কীভাবে তৈরি হয়?

সব ধরন এক file-এ define (utils/notificationEvents.js, 47টা) — title, message, link, priority, dedupe key। কোনো event ঘটলে services/notificationService.js সেটা তৈরি করে; একই key দ্বিতীয়বার এলে unique index আটকায়। Client NotificationBell.jsx unread count দেখায় (GET /notifications/unread-count)।

Email fail করলে কি request fail হয়?

না। Email মূল কাজ সফল হওয়ার পরে যায়; fail হলে log হয়, কখনো error ছোঁড়ে না। পাঠানোর আগে email_log-এ key লেখা হয়, তাই retry বা দ্বিতীয় cron-এ একই email দুবার যায় না (services/emailService.js, template utils/emailTemplates.js)।

কোন কোন email যায়?

তিনটা: request received (আর pickup বদলালে), আগের দিনের pickup reminder, আর technician-কে নতুন job। Gmail SMTP (Nodemailer) দিয়ে; production-এ চালু।

১৬. Payment আরও গভীরে

Customer কত টাকা কখন দেয়? পুরো হিসাবটা বলো।

Choose করার সময় inspection fee 200 (Stripe)। Quote 4,000 approve করলে বাকি 3,800 (Stripe)। মোট 4,000। Technician পায় 4,000-এর 90% = 3,600, Sarabo 400। Fee আলাদা row-এ থাকে কিন্তু final price-এ credit হয়।

Fee কখন ফেরত, কখন রাখা হয়?

ফেরত: technician না এলে (no-show), booking fail হলে, customer pickup-এর ≥2 ঘণ্টা আগে cancel করলে। রাখা (90/10): দেরিতে cancel, quote decline করে close, not repairable। Report-এর Table "fee outcomes"-এ পুরোটা।

Stripe-এ BDT চলে? টাকার ভগ্নাংশ?

Test mode-এ BDT দিয়ে চালাই। সব হিসাব পূর্ণ টাকায় (integer) — commission integer ratio-তে, technician-এর অংশ বিয়োগ করে, তাই কখনো ০.৫ টাকা হারায় না।

PDF receipt কে দেখতে পারে?

শুধু যে payment করেছে আর admin; অন্য কেউ চাইলে 404। GET /payments/:transactionId/receipt.pdf → services/paymentReceipt.js (pdfkit) server-এ বানায়।

Payment success page কেন সাথে সাথে redirect করে না?

Receipt download করার সুযোগ দিতে; কয়েক সেকেন্ড পরে ফেরত নেয়, আর button দিয়ে repairs/payment history-তে যাওয়া যায়।

১৭. Technician আর admin process

Technician কীভাবে যোগ দেয়?

pages/BecomeTechnician/BecomeTechnician.jsx → POST /technicians: নাম, phone, NID, region/district, address, আর expertise (device, repair type, level, অভিজ্ঞতার বছর)। Admin ApproveTechnicians.jsx-এ approve/reject করে (PATCH /technicians/:id); approve হলে একই transaction-এ user-এর role technician (rider) হয়; admin account-এর role কখনো বদলায় না।

Technician কি নিজের email/NID বদলাতে পারে?

না — approval-এর সময় যাচাই করা, তাই admin-কে বলতে হয়। নাম, phone, area, address নিজে বদলাতে পারে (PATCH /technicians/me), কিন্তু active repair থাকলে area না।

কেউ admin হয় কীভাবে?

শুধু অন্য admin Users page থেকে "Make admin" দিয়ে (PATCH /users/:id/role, verifyAdmin)। Customer নিজে role বদলাতে পারে না; technician হয় শুধু approved application দিয়ে।

Admin কি সরাসরি technician assign করতে পারে?

হ্যাঁ, override হিসেবে (AssignTechnicians.jsx → PATCH /repair-requests/:id), কিন্তু শুধু matching rule যাদের eligible বলে (GET /repair-requests/:id/eligible-technicians)। সাধারণত admin invite পাঠায় (POST /admin/repair-requests/:id/invite), technician নিজে offer দেয়।

Request delete করা যায়?

শুধু একদম শুরুর অবস্থায় (technician নেই, payment নেই) — services/deletionPolicy.js। Delete করলে তার upload session আর storage-এর ছবিও মোছে। পরে শুধু cancel/close, যাতে টাকার record থাকে।

১৮. আরও "code দেখাও" walkthrough

Warranty claim খোলা থেকে শেষ পর্যন্ত code-এ কী হয়?

Customer CustomerWarrantySection.jsx → POST /repair-requests/:id/warranty-claims → warrantyController.openClaim(): claimEligibility() (30 দিনের মধ্যে? খোলা claim নেই? ২টার কম?) আর validateClaimInput() (utils/warranty.js)। Technician WarrantyClaims.jsx → schedule → decision (covered/not covered কারণসহ) → rerepair; customer confirm ("Working now") → resolved। Deadline cron-এ alertOverdueClaims(); admin adminRefund → services/warrantyRefunds.js।

Withdrawal request থেকে paid পর্যন্ত?

Wallet.jsx → POST /technician/withdrawals (bKash number 01XXXXXXXXX-এ normalise, amount ≤ available) → walletController.requestWithdrawal(), partial unique index একটার বেশি খোলা আটকায়। Admin WithdrawalRequests.jsx → POST /admin/withdrawals/:id/mark-paid TrxID সহ → processWithdrawal(); বা reject করলে টাকা আবার available।

Review দেওয়ার code?

components/feedback/customer/ReviewDialog.jsx → POST /repair-requests/:id/review → feedbackController.createReview(): শুধু receipt-confirmed repair-এর customer, প্রতি repair-এ একটা (unique index), 1–5 star, comment ≤1,000। Admin hide/restore করে ModerationDialog.jsx → PATCH /admin/technician-reviews/:id/visibility, history থাকে।

AI offer note লেখার code?

JobApplicationSheet.jsx-এর "Write it for me" → POST /repair-requests/:id/applications/ai-note → jobPortalController.aiNote() → services/aiOfferNoteService.js: Gemini-কে শুধু device, repair, সমস্যা আর technician-এর কয়েকটা শব্দ দেয়; উত্তর থেকে removeContactDetails() phone/email/link সরায়; ভাষা en/bn।

Technician job board-এ কোন job দেখবে, সেটা কোথায় ঠিক হয়?

GET /technician/job-portal → jobPortalController.listPortal(): technician-এর region আর expertise (utils/technicianExpertise.js) মিলিয়ে canTechnicianEverTakeRequest (services/technicianEligibilityService.js)। Public /jobs-এ সব open job-এর নিরাপদ summary।

১৯. Scaling আর "যদি…" প্রশ্ন

১০,০০০ user হলে কী ভাঙবে?

প্রথমে slot capacity (lock নেই), cron-এর batch limit, আর free tier (Gemini, Atlas)। সমাধান: atomic slot counter, cron-কে ছোট batch/queue-তে ভাগ, paid tier, public catalogue-এ cache। Code layered বলে এগুলো আলাদা করে বদলানো যায়।

বাংলাদেশের বাইরে নিতে চাইলে?

Region/district data, timezone (Asia/Dhaka), currency (BDT), payment gateway আর ভাষা বদলাতে হবে। এগুলো config/data-তে আলাদা আছে।

Mobile app বানাতে চাইলে?

API আলাদা আর REST, তাই React Native বা PWA একই API ব্যবহার করতে পারবে। Push notification যোগ করতে হবে।

Technician আর customer platform-এর বাইরে deal করে ফেললে?

পুরোপুরি আটকানো যায় না। কমাতে: public board-এ contact নেই, AI note থেকে phone/email সরানো, আর platform-এ থাকলে warranty, receipt, guaranteed payment — বাইরে গেলে এগুলো নেই।

ভুয়া review?

Review শুধু সেই customer দিতে পারে যার repair receipt-confirmed, প্রতি repair-এ একটা, আর edit/delete হয় না। Admin hide করতে পারে, কিন্তু rating বদলাতে পারে না।
