\section{Testing Strategy}
Testing focused on \emph{domain correctness}: whether the right person can do the right thing at the right time, exactly once. Four layers were used (Figure~\ref{fig:testlayers}).

\begin{figure}[htbp]
\centering
\begin{tikzpicture}[font=\small]

  \node[box,trapezium,trapezium angle=80,minimum width=8cm] (b) at (0,1.2) {Playwright browser tests (desktop + mobile)};
  \node[box,trapezium,trapezium angle=82,minimum width=10cm] (c) at (0,0) {Server integration tests over real HTTP and a real MongoDB replica set};
  \node[box,trapezium,trapezium angle=84,minimum width=12cm] (d) at (0,-1.2) {Static checks: ESLint, production build, CI on every push};
\end{tikzpicture}
\caption{Testing layers used in Sarabo}
\label{fig:testlayers}
\end{figure}

\paragraph*{Server integration tests.} A custom harness (\texttt{test-all.js}) starts its own API on a random port against an isolated test database, seeds role accounts, an approved technician and the catalogue, and calls endpoints over real HTTP, plus direct service checks. Stripe, Supabase, Gemini and email are injected fakes, so no external service or money is touched. Races are tested by firing competing requests at once (two admins assigning, a cancellation racing a payment, one webhook delivered several times): each must give exactly one winner and a consistent state.

\paragraph*{Browser tests.} Playwright runs a production build of the client against a faked API on desktop and mobile (Pixel~7) viewports, covering public pages, the jobs board (listing, filters, sorting, empty and error states), tracking (valid, unknown and invalid codes, server errors), sign-in forms and route protection.

\paragraph*{Continuous integration.} GitHub Actions runs the server suites on a throwaway MongoDB~8 replica set, and client lint, build and browser tests, on every push and pull request. On the final commits (server 16 October, client 14 October 2026) the server workflow passed and the client lint-and-build job passed; the client browser-test job failed once on GitHub while the same 58 tests pass locally on that commit (Table~\ref{tab:results}).

\section{Manual End-to-End Acceptance}
In August 2026 the core lifecycle (request, assign, inspect, quote, reject, revise, approve, pay, repair, complete, confirm receipt) was accepted by hand with three accounts and Stripe test cards, checking that all roles saw the same state and that money became available only after receipt. On 14 October 2026 the marketplace flow was walked through the same way with real customer, technician and admin accounts: AI-assisted request, offer with AI note, inspection-fee payment, pickup condition, inspection, quote, approve-and-pay, repair, hand-back, review, a warranty claim to resolution, and a bKash withdrawal marked paid. Chapter~\ref{ch:walkthrough} is the record of that run.

\section{Validation Boundary}
The automated results come from an isolated environment with fake providers. Payments use Stripe test mode, so no real money has moved, and there are no real customers yet. Load testing and a formal security audit were out of scope.
