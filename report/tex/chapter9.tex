\section{Testing Strategy}
The testing mainly checks that the business rules are right. In other words, can the right person do the right thing at the right time, and only once? I used four layers of testing (Figure~\ref{fig:testlayers}).

\paragraph*{Server integration tests.} A custom test harness (\texttt{test-all.js}) starts its own copy of the API on a random port, connected to a separate test database. It creates accounts for each role, an approved technician and the catalogue, and then calls the endpoints over real HTTP. It also checks some services directly. Stripe, Supabase, Gemini and email are all replaced with fakes, so the tests never touch an outside service or any money. To test race conditions, the harness sends competing requests at the same moment, for example two admins assigning the same request, a cancellation arriving together with a payment, or one webhook delivered several times. In every case there must be exactly one winner, and the data must end up consistent.

\paragraph*{Browser tests.} Playwright runs a production build of the client against a fake API, at both desktop and mobile (Pixel~7) screen sizes. The tests cover the public pages, the jobs board (the listing, filters, sorting, and the empty and error states), tracking (valid, unknown and invalid codes, and server errors), the sign-in forms and route protection.

\paragraph*{Continuous integration.} On every push and pull request, GitHub Actions runs the server suites on a throwaway MongoDB~8 replica set, and runs lint, the build and the browser tests for the client. On the final commits (16 October for the server and 14 October 2026 for the client), the server workflow passed and so did the client's lint-and-build job. The client's browser-test job failed once on GitHub, even though the same 58 tests pass locally on that commit (Table~\ref{tab:results}).

\section{Manual End-to-End Acceptance}
In August 2026 I tested the core lifecycle by hand with three accounts and Stripe test cards: request, assign, inspect, quote, reject, revise, approve, pay, repair, complete and confirm receipt. I checked that every role saw the same state, and that the money only became available after the customer confirmed receipt. On 14 October 2026 I went through the marketplace flow in the same way, using real customer, technician and admin accounts. This run covered an AI-assisted request, an offer with an AI note, the inspection-fee payment, the pickup condition, inspection, the quote, approve-and-pay, the repair, the hand-back, a review, a warranty claim through to its resolution, and a bKash withdrawal marked as paid. Chapter~\ref{ch:walkthrough} is the record of that run.

\section{Validation Boundary}
It is worth being clear about what these results do and do not show. The automated results come from an isolated environment with fake providers. Payments run in Stripe test mode, so no real money has changed hands, and the platform has no real customers yet. Load testing and a formal security audit were outside the scope of this project.
