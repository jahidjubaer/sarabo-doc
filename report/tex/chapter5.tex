\section{Frontend Implementation}
\subsection{Role-Aware Routing}
The dashboard is wrapped by an authenticated route and subdivided by role guards. Customers get Overview, Create Request, My Requests and Payment History; Technicians get Overview, Find jobs, Assigned jobs, Completed jobs and Wallet; Admins get Overview, Repair requests, Assign technicians, Technicians, Withdrawals, Users, Services \& prices, Reports, Technician reports and Technician reviews. Every role also has Notifications and Profile, and a bottom tab bar replaces the sidebar on phones. Deep links (for example \texttt{?category=smartphone}) survive the sign-in redirect. Routing is a convenience only; every protected endpoint re-checks authentication and authorization.

\subsection{Server-State Hooks}
Each feature has a query-key factory (for example \texttt{quoteKeys}, \texttt{repairKeys}, \texttt{walletKeys}) and hooks for reading and mutating. A mutation invalidates exactly the queries that become stale: approving a quote refreshes the quote, the request detail, the customer's request list and the payment eligibility. This keeps the three roles' views consistent without reloading the page.

\subsection{Action-First Workspace}
Each request page (for example Figure~\ref{fig:wt-c10}) shows the service spine at the top, then a ``next step'' panel that tells the signed-in role exactly what to do (for example ``Choose a technician: 2 offers waiting'' or ``Approve and pay BDT 2,300''), followed by supporting context. Reusable empty, loading, error, confirmation and form components keep behaviour consistent. A guided product tour introduces each dashboard on first visit, and a command menu allows keyboard navigation.

\section{Backend Implementation}
\subsection{Controllers, Services and Adapters}
Workflow endpoints live in domain controllers (for example \texttt{jobPortalController}, \texttt{quoteController}, \texttt{paymentController}). Logic used in more than one place lives in services such as \texttt{jobBooking}, \texttt{inspectionFeeRefunds}, \texttt{paymentEligibility}, \texttt{technicianMatchGate}, \texttt{notificationService} and \texttt{emailService}. External providers are reached through adapters (\texttt{supabaseBucketAdapter}, Gemini providers, Stripe client), which tests replace with fakes.

\subsection{Database Transactions}
Operations that update several dependent records use MongoDB transactions. Booking a technician after an inspection-fee payment, for instance, records the payment, sets the request to \texttt{driver\_assigned}, marks the technician busy, accepts the chosen offer and marks every other offer \texttt{not\_chosen}, all in one transaction (\texttt{services/jobBooking.js}). If any step fails, nothing changes.

\subsection{Notifications, Email and Scheduled Jobs}
Important events create in-app notifications through one service, each with a de-duplication key so that a retried request never notifies twice. Emails (request received, pickup reminder, new job offer) are sent through Gmail after the main action succeeds; a failed email is logged in \texttt{email\_log} and never fails the request. A daily Vercel Cron job, protected by a secret, posts ``pickup tomorrow'' reminders to customers and technicians and automatically closes requests whose declined quote has had no response for three days.

\section{Service Catalogue and Matching}
Admins edit services and prices from the dashboard. A price change increments \texttt{pricingRule.version}; existing requests keep their own price snapshot. Every service has an inspection fee of at least 100\,BDT, or 200\,BDT when its estimate tops out above 1,000\,BDT; the same rule (\texttt{minimumInspectionFee}) is applied to new requests, offers, the admin editor and the public price list, and a one-time migration raised the 16 live services that had no fee. When a customer creates a request, \texttt{technicianMatchGate} checks that at least one approved technician in the same region has the required device, repair and expertise level. If not, the API answers \texttt{409 NO\_TECHNICIAN\_AVAILABLE}, the form explains why, and the refused demand is counted once per customer, service, region and day (with the customer identity hashed) so admins can see where to recruit.

\section{Pickup Scheduling}
Customers pick one of four two-hour windows (10:00--18:00 Bangladesh time), Saturday to Thursday, at least one hour and at most seven days ahead. Each region accepts a configurable number of pickups per slot (default three); a full slot returns \texttt{409 PICKUP\_SLOT\_FULL}. The window can be changed until the device is collected, and a moved pickup is reminded again.

\section{Quotation Model}
A quote has whole-taka labour, parts and additional-charge amounts, a total, currency, version and status. If the customer rejects it, the rejected quote is moved to \texttt{quoteHistory} before the live quote is cleared, so the old decision stays auditable and can never be paid by mistake.

\begin{lstlisting}[caption={Quote total and amount still to pay},label={lst:quote}]
repairSubtotal   = laborAmount + partsAmount + additionalCharges
quote.totalAmount = repairSubtotal            (currency "BDT")
amountDue        = max(quote.totalAmount - inspectionFeePaid, 0)
\end{lstlisting}

\section{Payment Implementation}
The server creates every Stripe Checkout session from stored data (the approved quote or the chosen offer's fee), never from an amount sent by the browser. Each session carries metadata saying what it pays for (\texttt{repair} or \texttt{inspection\_fee}). The signed webhook, and the success page as a fallback, both call the same idempotent processor, so a payment is recorded exactly once whichever arrives first. One shared server function decides whether a request is paid, and the same rule is used for payment eligibility, admin filters and list badges, so they can never disagree. Every payment row produces a PDF receipt (Stripe payment ID, date in Dhaka time, device, repair, technician, amount and refund status).

\section{Technician Settlement and Wallet}
When a repair is paid, a settlement snapshot is frozen from the approved quote:

\begin{lstlisting}[caption={Settlement rule (whole taka)},label={lst:settlement}]
commission  = round(repairSubtotal * 10 / 100)    # Sarabo
receivable  = repairSubtotal - commission          # Technician
# invariant: commission + receivable == repairSubtotal
\end{lstlisting}

The settlement stays \emph{pending} until the customer confirms receipt, then becomes \emph{available}. Wallet balances are never stored as a running number; they are recomputed from settlement snapshots and withdrawal records, so they cannot drift. A technician requests a withdrawal up to the available balance, giving a bKash number; an admin sends the money with bKash ``Send Money'' and records the transaction ID (TrxID) when marking it paid. A unique partial index allows only one open withdrawal per technician.

\section{Damage and Evidence Images}
Images go directly from the browser to a private Supabase bucket through a signed upload URL (JPEG, PNG or WebP, up to 8\,MB, at most three per request). The server then reads the stored object's real type and size before attaching it, and returns fresh five-minute signed read URLs only to the owner, an admin or the currently assigned technician. When a request is deleted, storage clean-up is retried in the background until it succeeds.

\section{Public Tracking and Jobs Board}
New requests get a tracking code \texttt{SRB-<random>} with 128 bits of randomness. \texttt{GET /public/trackings/:code} returns only the status timeline and timestamps, is rate limited and accepts only exact codes. The public jobs board (\texttt{GET /jobs}, 60 requests per minute per address) lists open requests with device, repair, area, pickup day, usual price and number of offers, but never the problem text, photos, tracking code or any personal detail.

\section{Deployment and Continuous Integration}
The API is deployed as a Vercel serverless function (Node.js 24) at \url{https://sarabo-server.vercel.app}, and the client as a static Vercel site at \url{https://sarabo-client-six.vercel.app}; both deploy automatically from the \texttt{main} branch. The API runs in Vercel's Mumbai region (\texttt{bom1}), next to the MongoDB Atlas cluster: this cut the first request after an idle period from 10.7\,s to 2.9\,s and a normal request from 0.75\,s to about 0.2\,s. Production uses its own database name, and the server refuses to start in production without the required secrets and an \texttt{https} client origin. GitHub Actions runs on every push: for the server, the full test suites against a throwaway MongoDB replica set started inside the job (CI is never given the real database credentials); for the client, ESLint and a production build. Pushing to \texttt{main} is a deliberate step taken only after all checks pass.
