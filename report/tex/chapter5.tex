\section{Frontend Implementation}
\subsection{Role-Aware Routing}
The dashboard sits behind an authenticated route with role guards. Customers get Overview, Create Request, My Requests and Payment History; Technicians get Overview, Find jobs, Assigned jobs, Completed jobs, Warranty claims and Wallet; Admins get Overview, Repair requests, Assign technicians, Technicians, Withdrawals, Warranty claims, Users, Services \& prices, Reports, Technician reports and Technician reviews. All roles have Notifications and Profile; phones get a bottom tab bar. Deep links (e.g.\ \texttt{?category=smartphone}) survive sign-in. Routing is only a convenience: every protected endpoint re-checks authentication and authorization.

\subsection{Server-State Hooks}
Each feature has a query-key factory (e.g.\ \texttt{quoteKeys}, \texttt{walletKeys}) and read/mutate hooks. A mutation invalidates exactly the stale queries (approving a quote refreshes the quote, the request, the request list and payment eligibility), so all three roles stay consistent without page reloads.

\subsection{Action-First Workspace}
Each request page (e.g.\ Figure~\ref{fig:wt-c10}) shows the service spine, then a ``next step'' panel telling the signed-in role what to do (e.g.\ ``Choose a technician'' or ``Approve and pay BDT 3,800''), then supporting details. Shared empty, loading, error, confirmation and form components keep behaviour consistent; a product tour introduces each dashboard, and a command menu supports keyboard navigation.

\section{Backend Implementation}
\subsection{Controllers, Services and Adapters}
Endpoints live in domain controllers (e.g.\ \texttt{jobPortalController}, \texttt{quoteController}, \texttt{paymentController}); shared logic lives in services such as \texttt{jobBooking}, \texttt{inspectionFeeRefunds}, \texttt{paymentEligibility}, \texttt{technicianMatchGate} and \texttt{notificationService}. External providers sit behind adapters (Supabase, Gemini, Stripe) that tests replace with fakes.

\subsection{Database Transactions}
Updates to several dependent records use MongoDB transactions. Booking after an inspection-fee payment, for instance, records the payment, sets the request to \texttt{driver\_assigned}, marks the technician busy, accepts the chosen offer and marks the others \texttt{not\_chosen} in one transaction (\texttt{services/jobBooking.js}); if any step fails, nothing changes.

\subsection{Notifications, Email and Scheduled Jobs}
Events create in-app notifications through one service, with de-duplication keys so a retry never notifies twice. Emails (request received, pickup reminder, new job) go through Gmail after the main action; a failed email is logged in \texttt{email\_log} and never fails the request. A daily Vercel Cron job (\texttt{GET /cron/pickup-reminders} at 12:00 UTC, 18:00 in Bangladesh), protected by a secret, sends the next day's pickup reminders and applies every deadline in Section~\ref{sec:nostuck}: it closes declined and unpaid quotes nobody acted on, confirms receipts the customer left unanswered for three days, and alerts admins to late warranty steps and stalled work. Each step runs on its own, so one failure does not stop the others. Email and the daily job are both switched on in production, so the live site sends reminders by email as well as in the app.

\section{Service Catalogue and Matching}
Admins edit services and prices from the dashboard; a price change increments \texttt{pricingRule.version}, while existing requests keep their price snapshot. Every service has an inspection fee of at least 100\,BDT (200\,BDT when its estimate tops out above 1,000\,BDT). One rule, \texttt{minimumInspectionFee}, applies to requests, offers, the editor and the public price list, and a one-time migration raised the 16 live services that had no fee. On request creation \texttt{technicianMatchGate} checks that an approved technician in the region has the required device, repair and level; if not, the API answers \texttt{409 NO\_TECHNICIAN\_AVAILABLE} and the refused demand is counted once per customer, service, region and day (customer hashed), showing admins where to recruit.

\section{Pickup Scheduling}
Customers pick one of four two-hour windows (10:00--18:00 Bangladesh time), Saturday to Thursday, one hour to seven days ahead. Each region takes a configurable number of pickups per slot (default three; a full slot returns \texttt{409 PICKUP\_SLOT\_FULL}). The window can change until collection, and a moved pickup is reminded again.

\section{Quotation Model}
A quote has whole-taka labour, parts and additional charges, a total, currency, version and status. A rejected quote moves to \texttt{quoteHistory} before the live quote is cleared, so it stays auditable and can never be paid by mistake.

\begin{lstlisting}[caption={Quote total and amount still to pay},label={lst:quote}]
repairSubtotal   = laborAmount + partsAmount + additionalCharges
quote.totalAmount = repairSubtotal            (currency "BDT")
amountDue        = max(quote.totalAmount - inspectionFeePaid, 0)
\end{lstlisting}

\section{Payment Implementation}
Every Stripe Checkout session is created from stored data (the approved quote or the chosen offer's fee), never from a browser amount, and its metadata says what it pays for (\texttt{repair} or \texttt{inspection\_fee}). The signed webhook and, as a fallback, the success page call the same idempotent processor, so a payment is recorded exactly once. One server function decides whether a request is paid, used by eligibility, admin filters and badges alike. Each payment has a PDF receipt (Stripe ID, Dhaka-time date, device, repair, technician, amount, refund status).

\section{Technician Settlement and Wallet}
When a repair is paid, a settlement snapshot is frozen from the approved quote:

\begin{lstlisting}[caption={Settlement rule (whole taka)},label={lst:settlement}]
commission  = round(repairSubtotal * 10 / 100)    # Sarabo
receivable  = repairSubtotal - commission          # Technician
# invariant: commission + receivable == repairSubtotal
\end{lstlisting}

The settlement stays \emph{pending} until the customer confirms receipt, then becomes \emph{available}. Balances are never stored; they are recomputed from settlements and withdrawals, so they cannot drift. A technician withdraws up to the available balance to a bKash number; an admin sends it by bKash Send Money and records the TrxID. A unique partial index allows one open withdrawal per technician.

\section{Damage and Evidence Images}
Images go straight from the browser to a private Supabase bucket via a signed upload URL (JPEG, PNG or WebP, up to 8\,MB, three per request). The server checks the stored object's real type and size before attaching it, and gives five-minute signed read URLs only to the owner, an admin or the assigned technician. Storage clean-up after deletion is retried until it succeeds.

\section{Public Tracking and Jobs Board}
Each request gets a tracking code \texttt{SRB-<random>} with 128 bits of randomness; \texttt{GET /public/trackings/:code} (exact codes, rate limited) returns only the status timeline. The jobs board (\texttt{GET /jobs}, 60 requests per minute per address) shows device, repair, area, pickup day, usual price and offer count, never the problem text, photos, tracking code or personal details.

\section{Deployment and Continuous Integration}
The API is a Vercel serverless function (Node.js 24) at \url{https://sarabo-server.vercel.app} and the client a static Vercel site at \url{https://sarabo-client-six.vercel.app}; both deploy from \texttt{main}. The API runs in Vercel's Mumbai region (\texttt{bom1}), next to the MongoDB Atlas cluster, which cut the first request after idle from 10.7\,s to 2.9\,s and a normal one from 0.75\,s to about 0.2\,s. Production has its own database, and the server will not start there without its secrets and an \texttt{https} client origin. GitHub Actions runs on every push: the server suites on a throwaway MongoDB replica set (never with real credentials), and client lint, build and browser tests. Pushing to \texttt{main} happens only after all checks pass.
