\chapter{Security, Reliability and Data Integrity}

\section{Security Principles}
Sarabo is \emph{server-authoritative}: the client decides what to show, the server what is allowed, enforcing authorization at every resource operation~\cite{owasprest}. Secrets (database, Stripe, Supabase, Gemini, Gmail, cron) live only in server environment variables, never in the repository or the browser.

\section{Authentication}
Each protected request carries a Firebase ID token, verified on the server with Firebase Admin; the caller's email comes only from that token, so endpoints such as \texttt{/technicians/me} or the wallet never take another user's email as input. Creating requests or payments needs a verified email address.

\section{Role- and State-Based Authorization}
Every write endpoint checks both who the caller is and what state the request is in:
\begin{itemize}
  \item only Admins approve technicians, edit the catalogue, retry refunds, process withdrawals and moderate feedback;
  \item only an approved, matching Technician can see job details or send an offer, and only the booked Technician can inspect, quote, revise and repair;
  \item only the owning Customer can choose or reject offers, decide on a quote, pay, cancel, confirm receipt and review;
  \item a quote can be submitted only after inspection, payment only after approval, revision only from \texttt{quote\_rejected}, and a paid repair can never re-enter the rejected-quote path.
\end{itemize}
Requests that do not belong to the caller return the same ``not found'' answer as missing ones, so their existence is not revealed.

\section{Financial Integrity}
Prices, fees, credits, commissions, balances and withdrawal limits are derived on the server from stored data, in whole taka. Stripe sessions use stored amounts, the webhook signature is checked on the raw body~\cite{stripewebhooks}, payments and refunds are idempotent, settlements are frozen once, and a withdrawal moves to \emph{paid} or \emph{rejected} through a single-winner update, so it can never be paid twice.

\section{Privacy}
Public endpoints (tracking, jobs board, availability) return purpose-built projections with no names, emails, addresses, phone numbers, payment data or database IDs. Technicians see only the district and problem until booked; refused-demand counts store a hash, not the email; reports about technicians are admin-only.

\section{Private Image Security}
The bucket is private; signed URLs are short-lived and per object; the server checks the real stored type and size, and never returns the permanent object identifier.

\section{Input Validation and Safe Errors}
The server validates IDs, transitions, amounts, text lengths, file types and each mutation's allowed fields, rejecting anything unexpected; user text is stored and shown as plain text. Errors use stable codes (e.g.\ \texttt{PICKUP\_SLOT\_FULL}) instead of raw provider messages, and logs keep only request ID, route, status and a category, never bodies or secrets.

\section{CORS, Rate Limiting and Abuse Control}
The API accepts browser calls only from the configured \texttt{https} client origin. Tracking, the jobs board and all AI features are rate limited, with AI limits stored in MongoDB so they hold across serverless instances; the scheduled job refuses to run without its secret.

\section{Transaction Safety}
MongoDB transactions protect the invariants that matter most:
\begin{itemize}
  \item a request's state and its technician's availability always agree, so a technician cannot be double-booked;
  \item a payment, the booking it causes and the offers it closes change together;
  \item a quote transition, its tracking event and its notification apply together or not at all;
  \item a fee refund is marked pending in the same transaction as the event that causes it.
\end{itemize}
A late defect (Appendix~\ref{app:incident}) showed a subtle rule: a duplicate-key error inside a transaction has already aborted it, so it must be passed on for the driver to retry, never swallowed.

\section{Environment Isolation}
Development, tests and production use different databases, and tests refuse to run against development or production. Seed and migration scripts default to dry runs and need explicit one-time flags for production; CI uses a throwaway database and no real credentials.

\section{Legacy Compatibility Boundary}
Some stored values come from the original parcel-delivery codebase (the role \texttt{rider}, statuses such as \texttt{driver\_assigned} or \texttt{parcel\_delivered}). They are frozen contract values behind a presentation layer, so users only see repair terms; renaming them needs a data migration (future work).
