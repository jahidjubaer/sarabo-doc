\chapter{System Design and Architecture}

\section{High-Level Architecture}
Sarabo follows a browser-client / API-server architecture with external services for identity, payment, storage, email and AI (Figure~\ref{fig:arch}). The React client is hosted on Firebase Hosting; the Express API runs as a serverless function on Vercel, which also triggers a daily scheduled job. MongoDB Atlas holds all application data.

\section{Client Architecture}
The client (about 337 source files) is organised around five concerns:
\begin{enumerate}
  \item \textbf{Routing and guards}: public pages (home, services, service areas, jobs board, tracking, about, become a technician), authentication pages, and a dashboard subdivided by \texttt{CustomerRoute}, \texttt{TechnicianRoute} and \texttt{AdminRoute}. Guards improve usability only; the server enforces every rule again.
  \item \textbf{Feature components}: request creation and the AI helper, damage images, pickup slots, job offers, inspection, quotation, payment, repair, feedback, wallet, notifications, support chat and administration.
  \item \textbf{Server-state hooks}: TanStack Query hooks with central query-key factories provide caching, loading and error states, mutations and targeted invalidation.
  \item \textbf{Presentation utilities}: status-to-stage mapping (the ``service spine''), currency formatting, eligibility helpers and per-action error messages.
  \item \textbf{Design system}: shared tokens (colours, type scale, radii), light and dark themes, and reusable primitives built on Radix UI.
\end{enumerate}

\section{Server Architecture}
The server (about 191 JavaScript files including tests) is layered as \emph{routes} $\rightarrow$ \emph{middleware} $\rightarrow$ \emph{controllers} $\rightarrow$ \emph{services} / \emph{utilities} $\rightarrow$ \emph{database}. Middleware attaches a request ID, logs safely, verifies the Firebase token and waits for the database connection. Controllers own the state rules of one domain; services hold logic shared by several endpoints (payment eligibility, job booking, refunds, settlement, notifications, matching, AI calls, email). External providers (Stripe, Supabase, Gemini, Gmail) sit behind small adapters, so automated tests can inject fakes and never contact the real services.

The Stripe webhook route is registered before the global JSON parser because signature verification needs the exact raw request body. Routes stay registered even if the database is briefly unavailable; database-backed requests then fail with a controlled 503 instead of a misleading 404.

\section{Repair Request Document}
Modern requests carry \texttt{schemaVersion: 2}. Device identity is a structured \texttt{product} snapshot (category, brand, model) and the chosen service is copied together with its price rule, so later catalogue edits never change an existing request. \section{State Model}
The stored status field \texttt{deliveryStatus} and several of its values were inherited from the original parcel-delivery codebase. They are kept as a frozen internal contract, while all user-facing labels use repair terminology (Table~\ref{tab:states}).

\midrule

A job application (offer) has its own states: \texttt{pending}, \texttt{accepted}, \texttt{not\_chosen}, \texttt{withdrawn}, \texttt{no\_show} and \texttt{declined}. A settlement moves from \emph{pending} to \emph{available}, and a withdrawal from \emph{requested} to \emph{paid} or \emph{rejected}.

\section{The Service Spine}
The interface compresses the detailed states into four stages that customers understand (Figure~\ref{fig:spine}). The same component appears horizontally on the home page and vertically on the tracking page and in the dashboards. Receipt confirmation is shown as a hand-over action after ``Repaired'' rather than as a fifth stage.
