\section{Client Architecture}
The client (about 337 source files) is organised around five concerns:
\begin{enumerate}
  \item \textbf{Routing and guards}: public pages (home, services, areas, jobs, tracking, about, become a technician), sign-in pages, and a dashboard split by \texttt{CustomerRoute}, \texttt{TechnicianRoute} and \texttt{AdminRoute}; the server re-checks every rule.
  \item \textbf{Feature components}: request and AI helper, photos, pickup slots, offers, inspection, quote, payment, repair, warranty, feedback, wallet, notifications, support chat, administration.
  \item \textbf{Server-state hooks}: TanStack Query with central query keys for caching, loading and error states, mutations and targeted invalidation.
  \item \textbf{Presentation utilities}: the status-to-stage ``service spine'', currency formatting, eligibility helpers, per-action error messages.
  \item \textbf{Design system}: shared tokens, light and dark themes, and Radix UI primitives.
\end{enumerate}

\section{Server Architecture}
The server (about 191 JavaScript files with tests) is layered \emph{routes} $\rightarrow$ \emph{middleware} $\rightarrow$ \emph{controllers} $\rightarrow$ \emph{services} / \emph{utilities} $\rightarrow$ \emph{database}. Middleware adds a request ID, logs safely, verifies the Firebase token and waits for the database. Controllers own one domain's state rules; services hold shared logic (eligibility, booking, refunds, settlement, notifications, matching, AI, email); external providers sit behind adapters that tests replace with fakes.

The Stripe webhook route is registered before the JSON parser, since signature checks need the raw body. Routes stay registered while the database is briefly down, so requests fail with a controlled 503, not a misleading 404.

\section{State Model}
The status field \texttt{deliveryStatus} and several values come from the original parcel-delivery codebase; they are a frozen internal contract, and users see only repair terms (Table~\ref{tab:states}).

A job application (offer) has its own states: \texttt{pending}, \texttt{accepted}, \texttt{not\_chosen}, \texttt{withdrawn}, \texttt{no\_show} and \texttt{declined}. A settlement moves from \emph{pending} to \emph{available} (or to \emph{reversed} after a refund), a warranty claim from \emph{submitted} through re-inspection and decision to \emph{resolved} or \emph{refunded}, and a withdrawal from \emph{requested} to \emph{paid} or \emph{rejected}.

\section{The Service Spine}
